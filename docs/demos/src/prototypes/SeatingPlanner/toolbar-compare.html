Toolbar at mobile — three options

The action bar wraps to four ragged lines at 390px. These are options A, C and E, built as real working files rather than mockups: every action still opens its real modal in each one.

Read this first — the earlier numbers were wrong

This board originally measured at 500px and rendered its frames at 534px, because the grid used minmax(min(390px, 100%), 1fr) — 390 as a minimum, then stretched. A real phone has 144px less room than that, and the difference is not cosmetic: it changed which option wins. At 500px A and E tied and E was recommended. At 390px E is the weakest of the three and C is the only option that reaches two lines. Everything below is measured at real device widths.

Scope, unchanged: the toolbar is part of the problem, not all of it. At 390px the first table card sits at 592px — the event bar and plans strip above it account for most of that, and they are untouched here.

The trade-offs

C — sticky bottom bar now recommended

Actions leave the scroll region and dock to the bottom in four equal columns; the toolbar keeps only what describes the view. Labels shorten to Add / Layout / Types / Export, each keeping an aria-label with the full text, and the export menu opens upward.

  • For: the only option that reaches two toolbar lines at real phone widths, ties A on space, and puts every action in thumb reach where it never scrolls away.
  • Against: spends 49px permanently. Four icon+short-label cells are tight at 360px — worth a look on a real handset before committing.
  • Open question: the mobile design mirrors the unassigned count into the pane head rather than using a docked bar. If a bar exists, does that count belong in it? Two docked bars would be one too many.

A — overflow menu

Room layout and Table types move into a ⋯ menu; the filter, Add table and Export stay out. Reuses the export menu’s own popover styles, so it is not a second pattern.

  • For: identical usable area to C without introducing a docked bar — the conservative choice, and the smallest change to the existing layout.
  • Against: still three lines at every real width, and a ⋯ is where features go to be forgotten.
  • If adopted: fix the shell’s split handler, which resolves its menu with one('[data-sp-split-menu]') — the first in the document. A second menu on those attributes would toggle the export menu. Latent today, real with two menus.

E — settings on the plan needs rework

Room layout and Table types are plan-scoped settings, not table-list actions, so they move beside New and Copy. The reasoning holds; this build does not. Below 430px the plans row wraps under four controls, so the height reappears just above the toolbar.

  • For: the only structural fix — nothing hidden, and it corrects a misplacement rather than working around it. Best of all four at 430px (368px usable).
  • Against: worst of the three from 360 to 412, which is where the users are.
  • To make it work: stop the plans row wrapping — all four controls icon-only below sm, or the two settings on the plan chip instead of the row. Worth doing if the principle matters more than the pixels.

Not covered by any of these

  • The event bar and plans strip, which are most of the 592px above the first card at 390px — the larger half of the mobile problem.
  • Real-handset checking. These are iframes at device widths, which is honest about layout but not about touch targets, thumb reach or how a docked bar feels next to a home indicator. C in particular should be opened on a phone before it is chosen.
  • Whether the plan title should truncate further; “· 30 tables” is already repeated in the pane head.
